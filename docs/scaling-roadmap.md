# 数据库与任务队列扩容路线

ScholarForge 当前采用 SQLite（WAL）和进程内任务协调，适合单实例早期部署。不要在没有迁移演练的情况下直接把多台应用实例连接到同一个 SQLite 文件。

## 触发迁移的信号

出现任一情况时启动迁移：需要两个或更多应用副本、写锁等待持续升高、后台任务需要跨实例恢复、备份窗口影响请求，或订单/支付写入量开始接近单机容量。

## 目标架构

- PostgreSQL：用户、订单、支付、项目、证据元数据和迁移版本。
- Redis + BullMQ：生成、解析、导出等后台任务；业务数据库保存最终状态，队列只负责调度。
- 对象存储：上传材料和生成文档；数据库只保存对象键、校验和与元数据。
- 应用实例保持无状态，限流使用 Redis 共享存储。

## 分阶段实施

1. 为数据库访问增加 repository 层，路由和服务不再直接依赖 better-sqlite3。
2. 生成 PostgreSQL schema，并为金额、时间、JSON、布尔值和外键建立明确映射。
3. 编写可重复运行的迁移程序：先导出 SQLite 快照，再导入 PostgreSQL，并校验每张表的行数、主键范围、外键和金额汇总。
4. 在 staging 做影子迁移和只读比对；至少完成一次备份恢复演练。
5. 短暂停写，执行最终增量迁移，切换 DATABASE_URL；保留 SQLite 快照用于回滚。
6. 将 AI 任务迁入 BullMQ，使用稳定 job id 保证幂等；支付回调仍以数据库唯一约束作为最终防线。
7. 接入 Redis 限流和对象存储，随后再增加应用副本。

## 上线门槛

- 迁移前后表行数、订单金额汇总和关键外键一致。
- 支付回调重复投递不会重复入账。
- Worker 崩溃后任务可重试，且不会重复收费或重复生成最终产物。
- staging 完成 PostgreSQL 备份恢复与回滚演练。
- 切换期间有明确维护窗口、负责人和回滚条件。

这是一条扩容路线，不代表当前单实例必须立即弃用 SQLite。
